# Contextualizing Vendor Alerts with Multi-Stage Behavioral Analytics in Google SecOps

## 1. Architectural Overview: How Multi-Stage UEBA Complements Curated Detections

The **Vendor Alerts** curated rule pack ingests and normalizes detections from integrated endpoint, network, firewall, cloud (CNAPP), email, and OT/IoT security vendors—allowing Google SecOps to surface third-party alerts within Chronicle.

Because third-party vendor appliances frequently generate high volumes of medium- and low-severity alerts without visibility into the surrounding 30-day enterprise behavioral baseline, this playbook enriches vendor alerts with **Multi-Stage Behavioral Analytics** (`secops-risk-metrics-multistage` and `secops-statistical-hunter`). The queries below fuse vendor alert telemetry with 30-day outbound byte baselines, Zipfian alert-signature fleet rarity, Dual-Baseline Fleet Delta-Z, and UDM Loopback Capstone correlation.

### Complementary Detection Layers
* **Curated Detections (Real-Time Deterministic & Single-Stage Layer)**: Provide immediate, low-latency alerting on high-confidence indicators, explicit attack syntax, and single-stage threshold breaches.
* **Multi-Stage UEBA & Statistical Hunting Harness (Cyclical Behavioral Layer)**: Extends coverage beyond the built-in window and observation constraints of single-stage rules through two architectural patterns executed by `PlaybookRunner` in `agentic-ueba`:
  1. **Option 1 — In-DAG Piecewise Cold-Start & Mature Baseline Unification**: Evaluates both newly active or dormant entities (`active_days <= 4` via a **Two-Part Zero-Inflated Hurdle** branch) and established entities (`active_days >= 5` via a **30-Day Parametric Z-Score** or **4-Stage Non-Parametric Median Absolute Deviation (MAD)** branch) inside a single unified YARA-L 2.0 query.
  2. **Option 3 — UDM Loopback Connective Tissue & Run-Scoped Capstone Convergence**: Every upstream query match is ingested back into Chronicle as a structured `PLAYBOOK_BEHAVIORAL_HUNT_MATCH` UDM event stamped with the execution cycle's unique `run_id` (`metadata.product_log_id`). Before the **Capstone Query** executes, `PlaybookRunner` validates via a read-after-write UDM search barrier (`verify_udm_run_indexed()`) that all upstream events are indexed, and then correlates entities exhibiting multi-scenario convergence ($\sum Z_i^2 \ge 25.0$).

## 2. Scenario-by-Scenario Breakdown & Verified Multi-Stage Queries

### Scenario 1: EDR Vendor Alert Pass-Throughs

* **Curated Detection Operational Focus**: Surfaces alert events generated by endpoint security agents across the fleet.
* **How Multi-Stage UEBA Extends Coverage**: Fuses 30-day endpoint alert baselines (`metrics.alert_event_name_count`) with 30-day outbound network bytes (`metrics.network_bytes_outbound`) ($D^2 \ge 12.25$) and weights alert signatures by Zipfian inverse host frequency ($I = \ln(N/df) \ge 3.2$).

#### Query 1A: 4-Stage Roll-Up Endpoint Alert + Outbound Network Bytes Fusion (`secops-risk-metrics-multistage`)
Compensates for static EDR severity passthroughs and unscored alerts by evaluating each host's 30-day per-rule alert baseline (`metrics.alert_event_name_count` keyed on `principal.asset.hostname` + `security_result.rule_name`), rolling up the peak per-rule Z-score per host, and fusing it with 30-day outbound network byte anomalies (`metrics.network_bytes_outbound`) via Euclidean threat distance ($D^2 = Z_{\text{alert}}^2 + Z_{\text{bytes}}^2 \ge 12.25$).

```yara
// ============================================================================
// Goal: Fuse 30-day per-rule endpoint alert anomalies with 30-day outbound network byte surges on the same host to isolate active post-alert exfiltration and C2.
// Statistical Model: 4-Stage Roll-Up Sector Fusion (metrics.alert_event_name_count + metrics.network_bytes_outbound, D^2 >= 12.25)
// ARCHITECTURE: 4-STAGE ROLL-UP SECTOR FUSION (COMPOSITE-ONLY METRIC + ENTITY-KEYED METRIC)
// Skill: secops-risk-metrics-multistage
// ADVISORY: Sector A (alert_event_name_count) is a composite-only roll-up sector; Z_a is the largest per-rule Z for the host, not a Z of total alert volume.
// ============================================================================

// --- STAGE 1: Sector A detail (UDM Source 1 of 2): one row per host and alert rule_name ---
stage sector_a_detail {
    (metadata.log_type = "CB_EDR" or metadata.log_type = "CS_EDR" or metadata.log_type = "MICROSOFT_GRAPH_ALERT" or metadata.log_type = "SENTINELONE_ALERTS")
    principal.asset.hostname = $entity
    $entity != ""
    security_result.rule_name = $security_result_rule_name
    $security_result_rule_name != ""

  match:
    $entity, $security_result_rule_name by 1d

  outcome:
    $d_obs = count(metadata.id)
    $d_avg = max(metrics.alert_event_name_count(
        period: 1d, window: 30d, metric: event_count_sum, agg: avg,
        principal.asset.hostname: principal.asset.hostname,
        security_result.rule_name: security_result.rule_name
    ))
    $d_std = max(metrics.alert_event_name_count(
        period: 1d, window: 30d, metric: event_count_sum, agg: stddev,
        principal.asset.hostname: principal.asset.hostname,
        security_result.rule_name: security_result.rule_name
    ))
    $d_days = max(metrics.alert_event_name_count(
        period: 1d, window: 30d, metric: event_count_sum, agg: num_metric_periods,
        principal.asset.hostname: principal.asset.hostname,
        security_result.rule_name: security_result.rule_name
    ))
    $d_z_raw = ($d_obs - $d_avg) / if($d_std > 0, $d_std, 1.0)
    $d_z = if($d_days >= 5 and $d_z_raw > 0, $d_z_raw, 0.0)
    $d_hot = if($d_days >= 5 and $d_z_raw >= 3.0, 1, 0)
    $d_novel = if($d_days = 0, 1, 0)
}

// --- STAGE 2: Sector A roll-up (stage-to-stage): one row per host ---
stage sector_a {
    $entity = $sector_a_detail.entity
    $ws = $sector_a_detail.window_start

  match:
    $entity, $ws by 1d

  outcome:
    $a_obs = sum($sector_a_detail.d_obs)
    $a_keys = count_distinct($sector_a_detail.security_result_rule_name)
    $a_hot_keys = sum($sector_a_detail.d_hot)
    $a_novel_keys = sum($sector_a_detail.d_novel)
    $a_days = max($sector_a_detail.d_days)
    $z_a = max($sector_a_detail.d_z)
}

// --- STAGE 3: Sector B — Outbound Network Bytes (UDM Source 2 of 2) ---
stage sector_b {
    network.sent_bytes > 0
    network.sent_bytes < 1000000000000000
    principal.asset.hostname = $entity
    $entity != ""

  match:
    $entity by 1d

  outcome:
    $b_obs = sum(network.sent_bytes)
    $b_avg = max(metrics.network_bytes_outbound(
        period: 1d, window: 30d, metric: value_sum, agg: avg,
        principal.asset.hostname: principal.asset.hostname
    ))
    $b_std = max(metrics.network_bytes_outbound(
        period: 1d, window: 30d, metric: value_sum, agg: stddev,
        principal.asset.hostname: principal.asset.hostname
    ))
    $b_days = max(metrics.network_bytes_outbound(
        period: 1d, window: 30d, metric: value_sum, agg: num_metric_periods,
        principal.asset.hostname: principal.asset.hostname
    ))
    $z_b_raw = ($b_obs - $b_avg) / if($b_std > 0, $b_std, 1.0)
    $z_b_pos = if($z_b_raw > 0, $z_b_raw, 0.0)
    $z_b = if($b_days >= 5, $z_b_pos, 0.0)
}

// --- ROOT STAGE: Roll-Up Sector Fusion & Distance Scoring ---
$entity = $sector_a.entity
$entity = $sector_b.entity
$ws = $sector_a.window_start
$ws = $sector_b.window_start

match:
  $entity, $ws by 1d

outcome:
  $a_observed = max($sector_a.a_obs)
  $a_keys = max($sector_a.a_keys)
  $a_hot_keys = max($sector_a.a_hot_keys)
  $a_novel_keys = max($sector_a.a_novel_keys)
  $b_observed = max($sector_b.b_obs)
  $b_active_days = max($sector_b.b_days)

  // Rectified, baseline-gated sector scores
  $z_a = max($sector_a.z_a)
  $z_b = max($sector_b.z_b)

  // Euclidean Vector Threat Norm D^2 = Z_a^2 + Z_b^2
  $z_a_sq = $z_a * $z_a
  $z_b_sq = $z_b * $z_b
  $composite_threat_norm_sq = $z_a_sq + $z_b_sq

condition:
  $composite_threat_norm_sq >= 12.25

order:
  $composite_threat_norm_sq desc
```

#### Query 1B: Zipfian Power-Law Fleet Rarity & Inverse Host Frequency Surprisal on EDR Alert Signatures (`secops-statistical-hunter`)
Compensates for unscored `trellix-hx` shards (`$risk_score = 0`), `sentinelone` catchall rules, and noisy fleet-wide `LOW`/`MEDIUM` alerts across CrowdStrike, Defender, SentinelOne, Trellix HX, and TrendMicro Vision One by ranking `security_result.rule_name` signatures in the asymptotic fleet tail ($\le 2$ hosts across the enterprise) weighted by local alert repetition intensity (`zipf_rarity_score >= 4.0`).

```yara
// ============================================================================
// Goal: Isolate rare third-party EDR alert signatures firing in the asymptotic fleet tail (<= 2 hosts) with high local repetition intensity across CrowdStrike, Defender, SentinelOne, Trellix HX, and TrendMicro Vision One.
// Target Telemetry: UDM_EVENTS (CS_DETECTS, CS_ALERTS, MICROSOFT_GRAPH_ALERT, SENTINELONE_ALERTS, TRELLIX_HX_ALERTS, TRENDMICRO_VISION_ONE)
// Statistical Model: Power-Law / Zipfian Inverse Host Frequency Rarity (zipf_rarity_score >= 4.0, adopter_hosts <= 2)
// ============================================================================

// Stage 1: Enterprise Fleetwide Alert Signature Popularity & Host Breadth
stage fleet_alert_popularity {
    (
      metadata.log_type = "CS_DETECTS"
      or metadata.log_type = "CS_ALERTS"
      or metadata.log_type = "MICROSOFT_GRAPH_ALERT"
      or metadata.log_type = "SENTINELONE_ALERTS"
      or metadata.log_type = "TRELLIX_HX_ALERTS"
      or metadata.log_type = "TRENDMICRO_VISION_ONE"
      or metadata.log_type = "TRENDMICRO_VISION_ONE_WORKBENCH"
      or metadata.log_type = "TRENDMICRO_VISION_ONE_DETECTIONS"
      or metadata.vendor_name = "SentinelOne"
    )
    principal.asset.hostname = $host
    $host != ""
    security_result.rule_name = $rule_sig
    $rule_sig != ""

  match:
    $rule_sig by 1d

  outcome:
    $fleet_hosts = count_distinct($host)
    $fleet_total_alerts = count(metadata.id)
}

// Stage 2: Endpoint Local Alert Signature Activity
stage endpoint_alert_burst {
    (
      metadata.log_type = "CS_DETECTS"
      or metadata.log_type = "CS_ALERTS"
      or metadata.log_type = "MICROSOFT_GRAPH_ALERT"
      or metadata.log_type = "SENTINELONE_ALERTS"
      or metadata.log_type = "TRELLIX_HX_ALERTS"
      or metadata.log_type = "TRENDMICRO_VISION_ONE"
      or metadata.log_type = "TRENDMICRO_VISION_ONE_WORKBENCH"
      or metadata.log_type = "TRENDMICRO_VISION_ONE_DETECTIONS"
      or metadata.vendor_name = "SentinelOne"
    )
    principal.asset.hostname = $host
    $host != ""
    security_result.rule_name = $rule_sig
    $rule_sig != ""

  match:
    $host, $rule_sig by 1d

  outcome:
    $endpoint_alerts = count(metadata.id)
    $sample_severities = array_distinct(security_result.severity)
}

// Root Stage: Zipfian Inverse Rank Departure & Asymptotic Tail Scoring
$rule_sig = $fleet_alert_popularity.rule_sig
$rule_sig = $endpoint_alert_burst.rule_sig
$host = $endpoint_alert_burst.host

match:
  $host, $rule_sig by 1d

outcome:
  $adopter_hosts = max($fleet_alert_popularity.fleet_hosts)
  $fleet_volume = max($fleet_alert_popularity.fleet_total_alerts)
  $local_volume = max($endpoint_alert_burst.endpoint_alerts)
  $severities = array_distinct($endpoint_alert_burst.sample_severities)

  // 1. Safe Cardinalities
  $safe_hosts = if($adopter_hosts > 0, $adopter_hosts, 1)
  $safe_volume = if($fleet_volume > 0, $fleet_volume, 1)

  // 2. Zipfian Power-Law Log-Rank Departure & Local Intensity
  $log_fleet = math.log($safe_volume)
  $log_adopters = math.log($safe_hosts)
  $log_local = math.log($local_volume + 1)
  $zipf_log_rank = ($log_fleet - $log_adopters) + $log_local

  // 3. Inverse Asymptotic Tail Multiplier
  $tail_rarity = 1.0 / $safe_hosts
  $zipf_rarity_score = $zipf_log_rank * (1.0 + $tail_rarity)

  // 6 Core Evidence Pillars
  $observation_count = $local_volume
  $baseline_active_samples = $fleet_volume
  $baseline_mean = $log_fleet
  $baseline_dispersion = $zipf_log_rank
  $fleet_prevalence = $adopter_hosts
  $distinct_binaries = 1

condition:
  $adopter_hosts <= 2
  and $local_volume >= 3
  and $zipf_rarity_score >= 4.0

order:
  $zipf_rarity_score desc
```

### Scenario 2: NDR & Firewall Vendor Alerts

* **Curated Detection Operational Focus**: Normalizes IDS/IPS, firewall, and network anomaly alerts from network security appliances.
* **How Multi-Stage UEBA Extends Coverage**: Fuses 30-day Failed HTTP and Total DNS query baselines ($D^2 \ge 12.25$) and applies 3-stage Dual-Baseline Fleet-Normalized Delta-Z ($\Delta Z \ge 3.0\sigma$) to suppress fleetwide scanner noise.

#### Query 2A: 3-Stage Dual-Sector Failed HTTP + Total DNS Queries Fusion (`secops-risk-metrics-multistage`)
Corroborates NDR and firewall alerts by fusing two independent 30-day network behavioral sectors on the same host (`principal.asset.hostname`): HTTP client/server error surges (`metrics.http_queries_fail`, capturing web exploit probing, C2 beacon 404/500 responses, and blocked proxy requests) and total DNS query surges (`metrics.dns_queries_total`, capturing DGA resolution and DNS C2 tunneling) with joint threshold $D^2 \ge 12.25$.

```yara
// ============================================================================
// Goal: Fuse 30-day failed HTTP request surges with 30-day total DNS query volume anomalies on the same host to corroborate NDR and firewall alerts.
// Statistical Model: 3-Stage Dual-Sector Threat Fusion (metrics.http_queries_fail + metrics.dns_queries_total, D^2 >= 12.25)
// ARCHITECTURE: 3-STAGE DUAL-SECTOR THREAT FUSION (GENERIC: ANY TWO ENTITY-KEYED METRICS)
// Skill: secops-risk-metrics-multistage
// ============================================================================

// --- STAGE 1: Sector A — Failed HTTP Queries (UDM Source 1 of 2) ---
stage sector_a {
    (network.http.method != "" or network.http.user_agent != "" or network.http.response_code != 0 or network.http.referral_url != "")
    network.http.response_code >= 400
    principal.asset.hostname = $entity
    $entity != ""

  match:
    $entity by 1d

  outcome:
    $a_obs = count(metadata.id)
    $a_avg = max(metrics.http_queries_fail(
        period: 1d, window: 30d, metric: event_count_sum, agg: avg,
        principal.asset.hostname: principal.asset.hostname
    ))
    $a_std = max(metrics.http_queries_fail(
        period: 1d, window: 30d, metric: event_count_sum, agg: stddev,
        principal.asset.hostname: principal.asset.hostname
    ))
    $a_days = max(metrics.http_queries_fail(
        period: 1d, window: 30d, metric: event_count_sum, agg: num_metric_periods,
        principal.asset.hostname: principal.asset.hostname
    ))
    $z_a_raw = ($a_obs - $a_avg) / if($a_std > 0, $a_std, 1.0)
    $z_a = if($z_a_raw > 0, $z_a_raw, 0.0)
}

// --- STAGE 2: Sector B — Total DNS Queries (UDM Source 2 of 2) ---
stage sector_b {
    (network.dns.questions.name != "" or network.dns.answers.name != "" or network.dns.id != 0)
    principal.asset.hostname = $entity
    $entity != ""

  match:
    $entity by 1d

  outcome:
    $b_obs = count(metadata.id)
    $b_avg = max(metrics.dns_queries_total(
        period: 1d, window: 30d, metric: event_count_sum, agg: avg,
        principal.asset.hostname: principal.asset.hostname
    ))
    $b_std = max(metrics.dns_queries_total(
        period: 1d, window: 30d, metric: event_count_sum, agg: stddev,
        principal.asset.hostname: principal.asset.hostname
    ))
    $b_days = max(metrics.dns_queries_total(
        period: 1d, window: 30d, metric: event_count_sum, agg: num_metric_periods,
        principal.asset.hostname: principal.asset.hostname
    ))
    $z_b_raw = ($b_obs - $b_avg) / if($b_std > 0, $b_std, 1.0)
    $z_b = if($z_b_raw > 0, $z_b_raw, 0.0)
}

// --- ROOT STAGE: Dual-Sector Threat Fusion & Distance Scoring ---
$entity = $sector_a.entity
$entity = $sector_b.entity

match:
  $entity by 1d

outcome:
  $a_observed = max($sector_a.a_obs)
  $b_observed = max($sector_b.b_obs)
  $a_active_days = max($sector_a.a_days)
  $b_active_days = max($sector_b.b_days)
  $z_a = max($sector_a.z_a)
  $z_b = max($sector_b.z_b)

  // Sparse-baseline gate: a sector with fewer active baseline days contributes 0
  $z_a_gated = if($a_active_days >= 5, $z_a, 0.0)
  $z_b_gated = if($b_active_days >= 5, $z_b, 0.0)

  // Euclidean Vector Threat Norm D^2 = Z_a^2 + Z_b^2
  $z_a_sq = $z_a_gated * $z_a_gated
  $z_b_sq = $z_b_gated * $z_b_gated
  $composite_threat_norm_sq = $z_a_sq + $z_b_sq

condition:
  $composite_threat_norm_sq >= 12.25

order:
  $composite_threat_norm_sq desc
```

#### Query 2B: 3-Stage Dual-Baseline Fleet-Normalized Delta-Z on NDR & Firewall Alerts (`secops-statistical-hunter`)
Replaces brittle regex scanner exclusions (`!= /Qualys|flood/`, `!= /THREAT - scan/`) with **3-Stage Dual-Baseline Population Normalization** ($\Delta Z = Z_{\text{personal}} - \max(0, Z_{\text{fleet}}) \ge 3.0\sigma$) across Corelight, Fortinet, Palo Alto, Trellix NX, and Vectra telemetry. When an enterprise vulnerability scan sweeps the fleet, $Z_{\text{fleet}}$ rises alongside $Z_{\text{personal}}$, driving $\Delta Z \to 0$; when a single host experiences a targeted intrusion or lateral movement surge while the fleet stays flat, $\Delta Z$ isolates the outlier.

```yara
// ============================================================================
// Goal: Isolate targeted host NDR and firewall alert surges from fleet-wide vulnerability scanner waves across Corelight, Fortinet, Palo Alto, Trellix NX, and Vectra.
// Target Telemetry: UDM_EVENTS (CORELIGHT, FORTINET_FORTIANALYZER, CORTEX_XDR, PAN_FIREWALL, FIREEYE_NX, VECTRA_DETECT, VECTRA_XDR)
// Statistical Model: 3-Stage Dual-Baseline Population Normalization (Delta-Z = Z_Personal - max(0, Z_Fleet_Shift) >= 3.0)
// ============================================================================

// Stage 1: Individual Host NDR/Firewall Alert Volume in tumbling hourly windows
stage host_hourly_extract {
    (
      metadata.log_type = "FORTINET_FORTIANALYZER"
      or metadata.log_type = "CORTEX_XDR"
      or metadata.log_type = "FIREEYE_NX"
      or metadata.log_type = "VECTRA_DETECT"
      or metadata.log_type = "VECTRA_XDR"
      or metadata.vendor_name = "Corelight"
      or metadata.vendor_name = "Palo Alto Networks"
    )
    principal.asset.hostname = $host
    $host != ""

  match:
    $host by 1h

  outcome:
    $hourly_count = count(metadata.id)
    $distinct_rules = count_distinct(security_result.rule_name)
}

// Stage 2: Individual Host Personal Historical Baseline (Temporal Baseline)
stage host_personal_baseline {
    $host = $host_hourly_extract.host

  match:
    $host

  outcome:
    $personal_avg = avg($host_hourly_extract.hourly_count)
    $personal_stddev = stddev($host_hourly_extract.hourly_count)
    $active_hours = count($host_hourly_extract.window_start)
}

// Stage 3: Concurrent Fleet-Wide Macro Baseline across all active endpoints in the same window
stage fleet_concurrent_baseline {
    $host = $host_hourly_extract.host
    $ws = $host_hourly_extract.window_start

  match:
    $ws by 1h

  outcome:
    $fleet_hour_avg = avg($host_hourly_extract.hourly_count)
    $fleet_hour_stddev = stddev($host_hourly_extract.hourly_count)
    $active_fleet_hosts = count_distinct($host_hourly_extract.host)
}

// Root Stage: Dual-Baseline Delta-Z Evaluation
$host = $host_hourly_extract.host
$host = $host_personal_baseline.host
$ws = $host_hourly_extract.window_start
$ws = $fleet_concurrent_baseline.ws

match:
  $host, $ws by 1h

outcome:
  // 6 Standardized Evidence Pillars
  $observation_count = max($host_hourly_extract.hourly_count)
  $baseline_active_samples = max($host_personal_baseline.active_hours)
  $baseline_mean = max($host_personal_baseline.personal_avg)
  $baseline_dispersion = max($host_personal_baseline.personal_stddev)
  $fleet_prevalence = max($fleet_concurrent_baseline.active_fleet_hosts)
  $distinct_binaries = max($host_hourly_extract.distinct_rules)

  // Dual-Baseline Metrics (Common Personal Dispersion Scale)
  $obs = max($host_hourly_extract.hourly_count)
  $p_mean = max($host_personal_baseline.personal_avg)
  $f_mean = max($fleet_concurrent_baseline.fleet_hour_avg)
  $raw_personal_sd = max($host_personal_baseline.personal_stddev)
  $safe_personal_sd = if($raw_personal_sd > 0, $raw_personal_sd, 1.0)

  $personal_z = ($obs - $p_mean) / $safe_personal_sd
  $f_shift = $f_mean - $p_mean
  $fleet_z = $f_shift / $safe_personal_sd
  $pos_fleet_z = if($fleet_z > 0, $fleet_z, 0.0)
  $delta_z = $personal_z - $pos_fleet_z

  $personal_z_score = $personal_z
  $fleet_concurrent_z = $fleet_z
  $targeted_delta_z = $delta_z

condition:
  $baseline_active_samples >= 3
  and $fleet_prevalence >= 2
  and $observation_count >= 5
  and $delta_z >= 3.0

order:
  $delta_z desc
```

### Scenario 3: OT / IoT & Network Asset Discovery Vendor Alerts

* **Curated Detection Operational Focus**: Ingests operational technology (OT), industrial control, and IoT anomaly alerts.
* **How Multi-Stage UEBA Extends Coverage**: Applies a Two-Part Zero-Inflated Hurdle model for dormant OT/IoT asset communication crossings and detects automated C2/polling anomalies via inter-arrival jitter ($\text{CV} \le 0.20$).

#### Query 3A: 2-Stage Hybrid 30-Day Outbound Network Bytes + `DERIVED_CONTEXT` Infant Asset Age (`secops-risk-metrics-multistage`)
Fuses 30-day host outbound network byte baselines (`metrics.network_bytes_outbound`) with the Chronicle **Entity Context Graph (`DERIVED_CONTEXT`)** asset `first_seen_time` to isolate newly discovered or rogue "infant" assets ($\le 7\text{ days}$ old) exhibiting immediate outbound volumetric anomalies, applying a $2.5\times$ threat score multiplier.

```yara
// ============================================================================
// Goal: Isolate newly discovered or rogue infant assets (first seen <= 7 days ago in DERIVED_CONTEXT) exhibiting anomalous outbound network byte volume.
// Statistical Model: 2-Stage Hybrid 30-Day Outbound Bytes Z-Score + DERIVED_CONTEXT Infant Asset Age (z_score >= 3.0, asset_age_days <= 7.0)
// ARCHITECTURE: 2-STAGE DUAL-PLANE DERIVED CONTEXT ASSET AGE PIPELINE
// Skill: secops-risk-metrics-multistage
// ============================================================================

// Stage 1: Macro 30-Day Host Outbound Network Byte Baseline (metrics.network_bytes_outbound)
stage stage1_asset_baseline {
    network.sent_bytes > 0
    network.sent_bytes < 1000000000000000
    principal.asset.hostname = $host
    $host != ""

  match:
    $host by 1d

  outcome:
    $observed_val = sum(network.sent_bytes)

    $hist_mean = max(metrics.network_bytes_outbound(
        period: 1d, window: 30d, metric: value_sum, agg: avg,
        principal.asset.hostname: principal.asset.hostname
    ))
    $hist_stddev = max(metrics.network_bytes_outbound(
        period: 1d, window: 30d, metric: value_sum, agg: stddev,
        principal.asset.hostname: principal.asset.hostname
    ))
    $hist_active_days = max(metrics.network_bytes_outbound(
        period: 1d, window: 30d, metric: value_sum, agg: num_metric_periods,
        principal.asset.hostname: principal.asset.hostname
    ))
    $event_timestamp = max(metadata.event_timestamp.seconds)
}

// Stage 2: Chronicle Derived Context Graph Lookup (Asset First Seen)
stage stage2_asset_derived_context {
    $asset.graph.metadata.source_type = "DERIVED_CONTEXT"
    $asset.graph.metadata.entity_type = "ASSET"
    $asset.graph.entity.asset.hostname = $host
    $host != ""

  match:
    $host

  outcome:
    $first_seen_ts = min($asset.graph.entity.asset.first_seen_time.seconds)
}

// Stage 3 (Root Stage): Fuses Host Anomaly Z-Score with Infant Asset Age Coloring
$host = $stage1_asset_baseline.host
$host = $stage2_asset_derived_context.host

match:
  $host by 1d

outcome:
  $observed = max($stage1_asset_baseline.observed_val)
  $mean = max($stage1_asset_baseline.hist_mean)
  $stddev = max($stage1_asset_baseline.hist_stddev)
  $z_score = ($observed - $mean) / if($stddev > 0, $stddev, 1.0)
  $active_baseline_days = max($stage1_asset_baseline.hist_active_days)

  $first_seen = min($stage2_asset_derived_context.first_seen_ts)
  $obs_ts = max($stage1_asset_baseline.event_timestamp)
  $raw_age_days = ($obs_ts - $first_seen) / 86400.0
  $asset_age_days = if($first_seen > 0, $raw_age_days, 9999.0)

  // Infant Asset Multiplier: 2.5x threat score boost for machines first seen <= 7 days ago
  $is_infant_asset = if($first_seen > 0 and $asset_age_days <= 7.0 and $asset_age_days >= 0.0, 1.0, 0.0)
  $threat_multiplier = if($is_infant_asset = 1.0, 2.5, 1.0)
  $threat_score = $z_score * $threat_multiplier

condition:
  $z_score >= 3.0
  and $asset_age_days <= 7.0

order:
  $threat_score desc
```

#### Query 3B: Poisson Fano Factor Burst Clustering on OT / IoT Vendor Alerts (`secops-statistical-hunter`)
Compensates for flat `by 1d` passthrough aggregation across `CLAROTY_CTD`, `CLAROTY_XDOME`, `FORESCOUT_EYEINSPECT`, and `NOZOMI_GUARDIAN` (`Nozomi Networks`) by modeling hourly alert arrival counts per asset (`principal.ip`) via the **Poisson Index of Dispersion / Fano Factor** ($F = \sigma^2 / \mu \ge 4.0$). Steady background OT protocol chatter yields $F \approx 1.0$, whereas concentrated OT reconnaissance scans, unauthorized PLC programming bursts, or rogue device probing produce extreme hourly over-dispersion ($F \ge 4.0$).

```yara
// ============================================================================
// Goal: Detect concentrated hourly bursts of OT, IoT, and NAC alerts per asset across Claroty, Forescout EyeInspect, and Nozomi Guardian using the Poisson Fano Factor.
// Target Telemetry: UDM_EVENTS (CLAROTY_CTD, CLAROTY_XDOME, FORESCOUT_EYEINSPECT, NOZOMI_GUARDIAN)
// Statistical Model: Poisson Dispersion via Fano Factor (F = sigma^2 / mu >= 4.0) & Fleet Prevalence Filter
// ============================================================================

// Stage 1: Hourly OT/IoT alert counts and distinct rule diversity per asset IP
stage hourly_ot_alerts {
    (
      metadata.log_type = "CLAROTY_CTD"
      or metadata.log_type = "CLAROTY_XDOME"
      or metadata.log_type = "FORESCOUT_EYEINSPECT"
      or metadata.log_type = "NOZOMI_GUARDIAN"
      or metadata.vendor_name = "Nozomi Networks"
    )
    principal.ip = $entity
    $entity != ""

  match:
    $entity by 1h

  outcome:
    $hourly_alerts = count(metadata.id)
    $distinct_rules = count_distinct(security_result.rule_id)
    $sample_targets = array_distinct(target.ip)
}

// Stage 2: Calculate historical arrival mean (mu), standard deviation (sigma), and active sample density
stage dispersion_baseline {
    $entity = $hourly_ot_alerts.entity

  match:
    $entity

  outcome:
    $mean_rate = avg($hourly_ot_alerts.hourly_alerts)
    $stddev_rate = stddev($hourly_ot_alerts.hourly_alerts)
    $total_alerts = sum($hourly_ot_alerts.hourly_alerts)
    $active_hours = count($hourly_ot_alerts.window_start)
    $max_rules = max($hourly_ot_alerts.distinct_rules)
}

// Stage 3: Measure enterprise-wide prevalence of OT/IoT assets alerting per hourly window
stage fleet_breadth {
    $ws = $hourly_ot_alerts.window_start

  match:
    $ws by 1h

  outcome:
    $fleet_assets = count_distinct($hourly_ot_alerts.entity)
}

// Root Stage: Join stages, calculate Fano Factor in outcome section, and emit 6 Evidence Pillars
$entity = $hourly_ot_alerts.entity
$entity = $dispersion_baseline.entity
$ws = $hourly_ot_alerts.window_start
$ws = $fleet_breadth.ws

match:
  $entity

outcome:
  // 6 Core Evidence Pillars
  $observation_count = max($dispersion_baseline.total_alerts)
  $baseline_active_samples = max($dispersion_baseline.active_hours)
  $baseline_mean = max($dispersion_baseline.mean_rate)
  $baseline_dispersion = max($dispersion_baseline.stddev_rate)
  $fleet_prevalence = max($fleet_breadth.fleet_assets)
  $distinct_binaries = max($dispersion_baseline.max_rules)
  $sample_commands = array_distinct($hourly_ot_alerts.sample_targets)

  // Aggregate Fano Factor (F = sigma^2 / mu)
  $raw_mean = max($dispersion_baseline.mean_rate)
  $safe_mean = if($raw_mean > 0, $raw_mean, 1.0)
  $raw_stddev = max($dispersion_baseline.stddev_rate)
  $variance = $raw_stddev * $raw_stddev
  $fano_factor = $variance / $safe_mean

condition:
  $baseline_active_samples >= 3
  and $observation_count >= 10
  and $baseline_mean >= 0.5
  and $fano_factor >= 4.0

order:
  $fano_factor desc
```

#### Query 4A: Two-Part Zero-Inflated Hurdle Model on Cloud & Email Vendor Alerts per User (`secops-statistical-hunter`)
Compensates for `wiz-threats` `$threat_id` collapsing, `trellix-helix` unaggregated floods, and `trellix-etp`/`trellix-ex` sender grouping by evaluating daily cloud and email vendor alert volume per user (`principal.user.userid`) via a **Two-Part Zero-Inflated Hurdle Model**. Accounts that are historically quiet/dormant ($\le 2$ active alert days in the lookback window) incur a discrete Bernoulli hurdle penalty when they suddenly accumulate multi-vendor alerts, while frequently alerting accounts are scored by their continuous intensity Z-score (`hurdle_threat_score >= 3.0`).

```yara
// ============================================================================

// Target Telemetry: UDM_EVENTS (WIZ_IO, FIREEYE_ETP, FIREEYE_EMPS, Trellix XDR)
// Statistical Model: Two-Part Hurdle Outlier Model for Zero-Inflated Telemetry (hurdle_threat_score >= 3.0)
// ============================================================================

// Stage 1: Historical daily cloud/email vendor alert extraction per user

    (
      metadata.log_type = "WIZ_IO"
      or metadata.log_type = "FIREEYE_ETP"

    $entity != ""

  match:
    $entity by 1d

  outcome:
    $bucket_count = count(metadata.id)
    $distinct_rules = count_distinct(security_result.rule_name)
}

// Stage 2: Historical active sample density and dispersion per user
stage entity_stats {
    $entity = $entity_historical.entity

  match:
    $entity

  outcome:
    $hist_mean = avg($entity_historical.bucket_count)
    $hist_stddev = stddev($entity_historical.bucket_count)
    $active_samples = count($entity_historical.window_start)
}

// Stage 3: Current window cloud/email alert activity per user
stage current_activity {
    (
      metadata.log_type = "WIZ_IO"
      or metadata.log_type = "FIREEYE_ETP"
      or metadata.log_type = "FIREEYE_EMPS"
      or metadata.product_name = "Trellix XDR"
    )
    principal.user.userid = $entity
    $entity != ""

  match:
    $entity by 1d

  outcome:
    $current_count = count(metadata.id)
    $current_rules = count_distinct(security_result.rule_name)
    $sample_products = array_distinct(metadata.product_name)

// Root Stage: Two-Part Hurdle Evaluation
$entity = $entity_stats.entity
$entity = $current_activity.entity
$window_start = $current_activity.window_start

outcome:
  // 6 Core Evidence Pillars

  $distinct_binaries = max($current_activity.current_rules)

  $diff = $observation_count - $baseline_mean
  $safe_stddev = if($baseline_dispersion > 0, $baseline_dispersion, 1.0)
  $intensity_z = $diff / $safe_stddev

  // 3. Composite Hurdle Threat Score (Option 1 Piecewise Unification)
  $hurdle_threat_score = if($is_dormant > 0, $dormant_score, $intensity_z)
  $unified_threat_score = $hurdle_threat_score

condition:
  $observation_count >= 3
  and $unified_threat_score >= 3.0

order:
  $unified_threat_score desc
```

#### Query 4B: 3-Stage Dual-Sector Auth Failures + Auth Successes Fusion (`secops-risk-metrics-multistage`)
Correlates cloud and email security alerts with downstream identity compromise by fusing 30-day baselines for failed logins (`metrics.auth_attempts_fail`) and successful logins (`metrics.auth_attempts_success`) per user (`target.user.userid`, $D^2 = Z_{\text{fail}}^2 + Z_{\text{success}}^2 \ge 12.25$). This surfaces brute-force/credential-stuffing waves that culminate in a successful account takeover after a Trellix ETP/EX phishing delivery or Wiz cloud credential exposure.

```yara
// ============================================================================
// Goal: Detect post-phishing and cloud-credential compromise account takeover by fusing 30-day authentication failure and authentication success anomalies per user.
// Statistical Model: 3-Stage Dual-Sector Threat Fusion (metrics.auth_attempts_fail + metrics.auth_attempts_success, D^2 >= 12.25)
// ARCHITECTURE: 3-STAGE DUAL-SECTOR THREAT FUSION (GENERIC: ANY TWO ENTITY-KEYED METRICS)
// Skill: secops-risk-metrics-multistage
// ADVISORY: Two metrics of the same auth family (auth_attempts_fail + auth_attempts_success) are paired to capture brute-force/stuffing followed by successful login takeover.
// ============================================================================

// --- STAGE 1: Sector A — Authentication Failures (UDM Source 1 of 2) ---
stage sector_a {
    metadata.event_type = "USER_LOGIN"
    not security_result.action = "ALLOW"
    target.user.userid = $entity
    $entity != ""

  match:
    $entity by 1d

  outcome:
    $a_obs = count(metadata.id)
    $a_avg = max(metrics.auth_attempts_fail(
        period: 1d, window: 30d, metric: event_count_sum, agg: avg,
        target.user.userid: target.user.userid

        period: 1d, window: 30d, metric: event_count_sum, agg: num_metric_periods,
        target.user.userid: target.user.userid
    ))
    $z_a_raw = ($a_obs - $a_avg) / if($a_std > 0, $a_std, 1.0)
    $z_a = if($z_a_raw > 0, $z_a_raw, 0.0)
}

// --- STAGE 2: Sector B — Authentication Successes (UDM Source 2 of 2) ---
stage sector_b {
    metadata.event_type = "USER_LOGIN"
    security_result.action = "ALLOW"
    target.user.userid = $entity
    $entity != ""

  match:
    $entity by 1d

  outcome:
    $b_obs = count(metadata.id)
    $b_avg = max(metrics.auth_attempts_success(
        period: 1d, window: 30d, metric: event_count_sum, agg: avg,
        target.user.userid: target.user.userid

        period: 1d, window: 30d, metric: event_count_sum, agg: stddev,
        target.user.userid: target.user.userid

        period: 1d, window: 30d, metric: event_count_sum, agg: num_metric_periods,

}

// --- ROOT STAGE: Dual-Sector Threat Fusion & Distance Scoring ---
$entity = $sector_a.entity
$entity = $sector_b.entity

match:
  $entity by 1d

outcome:
  $a_observed = max($sector_a.a_obs)
  $b_observed = max($sector_b.b_obs)
  $a_active_days = max($sector_a.a_days)
  $b_active_days = max($sector_b.b_days)
  $z_a = max($sector_a.z_a)
  $z_b = max($sector_b.z_b)

  // Sparse-baseline gate: a sector with fewer active baseline days contributes 0
  $z_a_gated = if($a_active_days >= 5, $z_a, 0.0)
  $z_b_gated = if($b_active_days >= 5, $z_b, 0.0)

  $z_a_sq = $z_a_gated * $z_a_gated
  $z_b_sq = $z_b_gated * $z_b_gated
  $composite_threat_norm_sq = $z_a_sq + $z_b_sq

condition:
  $composite_threat_norm_sq >= 12.25

order:
  $composite_threat_norm_sq desc
```

## 3. Appendix: A Practitioner's Plain-English Guide to the 8 Statistical Models

### 3.1 4-Stage Roll-Up Endpoint Alert + Outbound Network Bytes Fusion ($D^2 = Z_{\text{alert}}^2 + Z_{\text{bytes}}^2 \ge 12.25$ — Query 1A)
* **What it measures**: Whether a specific host is experiencing both an unusual surge in a specific EDR alert signature (`metrics.alert_event_name_count` keyed by host and `security_result.rule_name`) *and* an unusual surge in outbound network data transfer (`metrics.network_bytes_outbound`) on the same day.
* **Why static passthroughs fail**: Curated EDR rules (`crowdstrike`, `microsoft-defender`, `sentinelone`) fire on every event matching `severity = "HIGH"` or `"CRITICAL"`, generating thousands of repetitive alerts on developer/admin hosts without checking if the alert is abnormal for that host or accompanied by data exfiltration.
* **How the math works**: Because `metrics.alert_event_name_count` is a composite-only metric (requiring both `principal.asset.hostname` and `security_result.rule_name`), Stage 1 computes the 30-day Z-score for each `(host, rule_name)` pair, Stage 2 rolls up the highest per-rule Z-score (`$z_a`) per host, Stage 3 computes the host's 30-day outbound byte Z-score (`$z_b`), and the Root Stage fuses them via $D^2 = Z_a^2 + Z_b^2 \ge 12.25$ ($D \ge 3.5\sigma$).

### 3.2 Zipfian Power-Law Fleet Rarity & Inverse Host Frequency Surprisal (`zipf_rarity_score >= 4.0` — Query 1B)
* **What it measures**: How rare an EDR alert signature (`security_result.rule_name`) is across the entire workstation/server fleet (`$adopter_hosts <= 2`) combined with how intensely it is firing on a single endpoint (`$local_volume`).
* **Why static passthroughs fail**: `trellix-hx` shards 0–9 assign `$risk_score = 0` to every alert, and `sentinelone` catchall rules assign `$risk_score = 5`, burying targeted single-host detections underneath noisy rules that fire on hundreds of machines.
* **How the math works**: In any enterprise, benign EDR false positives follow a Zipfian power law—a handful of noisy signatures fire across dozens of hosts, while targeted attacker activity triggers signatures seen on only 1 or 2 endpoints. Computing $\big(\ln(N_{\text{fleet\_alerts}}) - \ln(N_{\text{hosts}}) + \ln(N_{\text{local}} + 1)\big) \times (1 + 1/N_{\text{hosts}})$ elevates rare, high-intensity endpoint alerts to the top of the triage queue.

### 3.3 3-Stage Dual-Sector Failed HTTP + Total DNS Queries Fusion ($D^2 = Z_{\text{http\_fail}}^2 + Z_{\text{dns}}^2 \ge 12.25$ — Query 2A)
* **What it measures**: Simultaneous 30-day anomalies in failed HTTP transactions (`metrics.http_queries_fail`, HTTP status $\ge 400$) and total DNS resolution volume (`metrics.dns_queries_total`) on the same endpoint.
* **Why static passthroughs fail**: NDR and NGFW passthrough rules (`corelight`, `fortinet`, `paloalto`, `trellix-nx`, `vectra`) alert on individual network signatures without verifying whether the host is actively beacon-probing or resolving C2 infrastructure.
* **How the math works**: Rectified, baseline-gated Z-scores ($\ge 5$ active days in the prior 30 days) for HTTP failures and DNS queries are combined into an orthogonal Euclidean threat norm $D^2 = Z_A^2 + Z_B^2 \ge 12.25$, catching hosts where both web and DNS planes deviate together.

### 3.4 3-Stage Dual-Baseline Fleet-Normalized Delta-Z ($\Delta Z = Z_{\text{personal}} - \max(0, Z_{\text{fleet}}) \ge 3.0\sigma$ — Query 2B)
* **What it measures**: How much a host's hourly NDR/firewall alert volume surged above its own historical mean *after subtracting any concurrent fleet-wide alert wave*.
* **Why static passthroughs fail**: `fortinet` and `paloalto` try to suppress vulnerability scanner noise using hardcoded string exclusions (`!= /Qualys|flood/`, `!= /THREAT - scan/`). Any scanner whose name is not hardcoded triggers a massive alert storm across every host in the subnet.
* **How the math works**: Stage 2 computes each host's personal hourly baseline ($\mu_p, \sigma_p$), while Stage 3 computes the concurrent fleet-wide hourly average ($\mu_f$). Subtracting the positive fleet shift $(\mu_f - \mu_p)/\sigma_p$ from the host's personal Z-score acts as a mathematical "Scanner Wave Immunity Shield"—suppressing scheduled enterprise scans while surfacing single-host lateral movement spikes.

### 3.5 2-Stage Hybrid 30-Day Outbound Network Bytes + `DERIVED_CONTEXT` Infant Asset Age (Query 3A)
* **What it measures**: Whether a host exhibiting a $\ge 3.0\sigma$ 30-day outbound network byte surge (`metrics.network_bytes_outbound`) is a newly discovered "infant" asset (`first_seen_time` $\le 7\text{ days}$ prior to the event timestamp in `DERIVED_CONTEXT`).
* **Why static passthroughs fail**: OT/IoT and NAC passthrough rules (`claroty`, `forescout`, `nozomi`) assign identical static risk scores to a 5-year-old building controller and a rogue device plugged into an industrial switch 2 hours ago.
* **How the math works**: Stage 1 computes the 30-day `metrics.network_bytes_outbound` Z-score; Stage 2 retrieves `min($asset.graph.entity.asset.first_seen_time.seconds)` from `DERIVED_CONTEXT`; the Root Stage calculates asset age in days relative to the event timestamp and applies a $2.5\times$ multiplier when `asset_age_days <= 7.0`.

### 3.6 Poisson Fano Factor Burst Clustering ($F = \sigma^2 / \mu \ge 4.0$ — Query 3B)
* **What it measures**: The hourly "clumpiness" or over-dispersion of OT/IoT/NAC alerts (`CLAROTY_CTD`, `CLAROTY_XDOME`, `FORESCOUT_EYEINSPECT`, `NOZOMI_GUARDIAN`) on an asset IP.
* **Why static passthroughs fail**: Aggregating `by 1d` with `condition: $e` collapses an intense 15-minute OT protocol scan or PLC command burst into the same single daily detection row as a routine once-a-day configuration warning.
* **How the math works**: Random background alerts follow a memoryless Poisson process where hourly variance equals the hourly mean ($F = \sigma^2 / \mu \approx 1.0$). Automated reconnaissance and exploit bursts pack dozens of alerts into 1–2 hours while remaining silent the rest of the day, driving $\sigma^2 / \mu \ge 4.0$.

### 3.7 Two-Part Zero-Inflated Hurdle Model (`hurdle_threat_score >= 3.0` — Query 4A)
* **What it measures**: Part 1 tests whether a user account (`principal.user.userid`) is historically dormant or zero-inflated ($\le 2$ active alert days) across cloud and email security telemetry (`WIZ_IO`, `FIREEYE_ETP`, `FIREEYE_EMPS`, `Trellix XDR`); Part 2 scores active accounts using their continuous historical Z-score.
* **Why static passthroughs fail**: `wiz-threats` collapses all affected users into `$threat_id by 1d`, `trellix-etp`/`trellix-ex` group by external sender rather than internal user, and `trellix-helix` fires unaggregated single-event alerts.
* **How the math works**: Separating *discrete activation* (crossing the zero hurdle from 0 alerts to $\ge 3$ alerts) from *continuous magnitude* prevents zero-inflation distortion and immediately highlights quiet cloud/email identities that suddenly accumulate multi-vendor alerts.

### 3.8 3-Stage Dual-Sector Auth Failures + Auth Successes Fusion ($D^2 = Z_{\text{fail}}^2 + Z_{\text{success}}^2 \ge 12.25$ — Query 4B)
* **What it measures**: The combined 30-day anomaly across failed login attempts (`metrics.auth_attempts_fail`) and successful login attempts (`metrics.auth_attempts_success`) for the same user (`target.user.userid`).
* **Why static passthroughs fail**: Email and cloud passthrough alerts notify the SOC that a phishing lure arrived or a cloud alert fired, but cannot tell whether the attacker subsequently brute-forced or hijacked the user's identity.
* **How the math works**: Pairing rectified 30-day Z-scores for authentication failures and authentication successes via $D^2 = Z_{\text{fail}}^2 + Z_{\text{success}}^2 \ge 12.25$ isolates the classic "spray/stuffing followed by login takeover" signature across all user accounts.
